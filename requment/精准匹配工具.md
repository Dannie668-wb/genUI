 精准匹配agent调用对应工具的策略有哪些                                                                                                 

● 几个主流方向，从轻到重：

  ---
  1. Prompt 工程（当前方案）

  靠 system prompt 的规则驱动模型行为。成本低，但依赖模型理解，容易被模糊输入绕过，规则多了互相干扰。适合简单、确定性高的场景。

  ---
  2. 结构化意图路由（Intent Router）

  在调用 LLM 之前，先用轻量分类器（规则/小模型/另一个 LLM prompt）判断用户意图，再决定走哪条工具链。LLM 只负责执行，不负责路由决策。

  用户消息 → Intent Classifier → ["select_shop", "order_item", "pay"]
                                        ↓
                               强制调用对应工具

  优点：确定性强，可单独测试。缺点：多一层调用，意图类目需要维护。

  ---
  3. Forced Tool Call（强制调用）

  LangChain / OpenAI 支持在调用时强制指定必须调用某个工具：

  llm.bind_tools(tools, tool_choice="get_menu")  # 强制调用 get_menu

  或用 tool_choice={"type": "function", "function": {"name": "get_menu"}} 精准指定。适合已知下一步必须调用某工具的场景（如已有 shop_id
  时）。

  ---
  4. 有限状态机（FSM）/ 工作流

  把对话流程建模成状态机，每个状态只暴露对应工具给 LLM，从根本上限制工具选择范围：

  State: NEED_ADDRESS    → 只有 request_location 可用
  State: NEED_SHOP       → 只有 search_nearby_shops 可用
  State: NEED_MENU       → 只有 get_menu 可用
  State: NEED_ORDER      → 只有 create_order 可用

  LangGraph 的节点/边本质就是这个模式。优点：精准可控，可审计。缺点：灵活性低，跳步场景处理复杂。

  ---
  5. 工具描述优化

  工具的 docstring 是模型选择工具的主要依据。描述越清晰、边界越明确，模型越少误调用：

  - 说清何时调用（触发条件）
  - 说清不应调用的情况
  - 参数名和类型要自描述

  这是成本最低、收益最高的优化，常被忽视。
